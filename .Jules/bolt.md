## 2025-10-10 - Prefer `count_memories()` SQL Aggregates Over `len(list_memories(...))`
**Learning:** `list_memories()` (and `query_memories()`) fetches full SQLite rows, parses JSON `metadata_json` per row, computes status and trust weights, constructs Python dicts, and sorts them. Calling `len(list_memories(limit=10000))` to compute total item counts for multiple categories (such as review queue totals) instantiates up to 40,000 dicts per request, taking ~135ms+. Using `count_memories(MemoryQuery.from_raw(...))` delegates counting directly to SQLite `SELECT COUNT(*)`, executing in ~7.8ms (~17x faster) with O(1) memory overhead.
**Action:** Always check if an aggregate helper like `count_memories()` exists before using `len(list_memories(...))` or `len(query_memories(...))` for counting UI badges, queue totals, or pagination meta.

## 2026-03-30 - Delegate Dashboard Series Aggregations to SQLite `GROUP BY`
**Learning:** Functions like `veracity_mix_series`, `source_breakdown_series`, `lifecycle_transition_series`, `session_activity_heatmap`, and `review_backlog_series` previously used `_bounded_memory_rows()` to load up to 10,000 full memory dicts from SQLite, parsing JSON metadata, enriching each dictionary, and sorting them in Python before computing counts. This took ~1.9s combined. Re-implementing these methods using direct SQLite `GROUP BY day` aggregations and targeted column selection reduced combined execution time to ~49ms (~39x speedup) with O(1) memory overhead.
**Action:** When computing time-series trends or category breakdowns from SQLite tables, perform `GROUP BY` and filtering directly in SQL rather than loading bounded in-memory object arrays.
